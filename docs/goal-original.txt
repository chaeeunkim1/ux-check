/goal GS건설 IT운영 담당자와 업무 시스템 담당자가 화면의 UI·UX 문제를 근거와 함께 발견하고 개발자에게 개선 요청을 전달할 수 있는 공개 웹 도구 ‘UX Check’를 완성한다. 작업 폴더는 D:\PLAI CAMP\ux-check, 공개 저장소는 https://github.com/chaeeunkim1/ux-check, 공개 운영 주소는 https://ux-check-zeta.vercel.app 이다. 이미 연결된 GitHub·Vercel·Claude API와 기존 로컬 환경변수를 사용한다. 지금부터 2026년 9월 22일 오전 10시(KST)까지 사용자의 추가 조작 없이 실질적인 개발·실행·검증·수정을 이어가고, 낮 12시 최종 제출을 위한 검토 가능한 결과물을 준비한다.

1. 해결할 문제와 사용자
GS건설 IT운영 담당자와 업무 시스템 담당자는 여러 업무 화면을 검수할 때 혼란스러운 정보 구조, 불명확한 버튼과 입력 안내, 놓치기 쉬운 상태·오류 표시 등을 수작업으로 찾아 설명하고 개발자에게 전달해야 한다. 기준과 근거가 흩어져 검수 시간이 길고 개선 요청이 주관적으로 전달된다. 화면 캡처와 사용자의 업무 목적을 입력하면 AI가 관찰 가능한 근거, 업무 영향, 우선순위, 구체적인 개선안을 일관된 보고서로 정리하도록 만든다.

2. 완료 상태
로그인 없이 공개 데모에서 합성 업무 화면 예제를 선택하거나 PNG/JPEG/WebP 화면 캡처를 올리고 업무 목적을 입력해 실제 Claude 분석을 실행할 수 있다. 결과에는 문제 위치 또는 해당 화면 요소, 관찰 근거, 영향, 심각도, 개선안, 확인이 필요한 사항이 표시된다. 사용자가 결과를 분류·확인하고 보고서를 내려받아 개발자에게 전달할 수 있다. 개선 전후 화면을 비교해 해결된 문제, 남은 문제, 새로 확인된 문제를 근거와 함께 검토할 수 있다. 예제는 승인 요청 목록, 입력 폼, 업무 대시보드 등 건설 업무를 연상할 수 있는 합성 데이터로 구성한다. 공개 데모와 GitHub 내용이 실제 구현 상태와 일치한다. 권장 약 1분·최대 3분의 공개 시연 영상, 결선 5분 발표에 사용할 자료, 문제와 아이디어 제출 문안, 실제 사용한 이 /goal 원문, 완료 범위와 한계 요약, 제출용 로그 내보내기 도구와 확인 기록을 준비한다.

3. 완료 확인 기준
빈 입력, 잘못된 형식, 용량 초과, 정상 이미지, API 오류·시간 초과, 재시도 흐름을 확인한다. 최소 세 종류의 합성 업무 화면에서 실제 API 분석을 실행하고 근거와 개선안이 화면 및 업무 목적에 맞는지 검토한다. 알려진 문제를 넣은 화면과 개선한 화면으로 비교 흐름을 확인하고, 검증 기준과 실제 관찰 결과를 기록한다. 판단하기 어려운 항목은 확인 필요로 표시하며 스크린샷만으로 동작, 접근성 준수, 사용자 행동을 확정하지 않는다. 보고서 다운로드 내용이 화면 결과와 일치해야 한다. 데스크톱과 모바일 화면, 키보드 주요 흐름, 로딩·오류·빈 상태를 확인한다. 의미 있는 자동 테스트, 프로덕션 빌드, 공개 배포의 주요 사용자 흐름이 통과해야 한다. 데모·영상·GitHub 세 링크는 인증 없는 새 브라우저 세션에서 실제 내용과 재생·동작을 확인하고 결과를 기록한다. 실행하지 못한 검증은 통과로 쓰지 않는다.

4. 제약
실제 회사·고객·직원 정보와 내부 화면, 회사 인증 정보는 사용하거나 공개하지 않는다. 공개 예제는 합성 데이터만 사용한다. API 키는 기존 서버 환경변수로만 사용하고 프런트엔드·GitHub·공개 보고서·영상에 포함하지 않는다. 사용자는 현재 Claude 키를 교체하지 않기로 했으므로 키 교체를 전제로 작업을 멈추지 않는다. 제출용 JSONL과 ZIP은 별도 사본에서 API 키 등 비밀값만 마스킹하고 재검사하며, 원본 로그와 실행 시간·토큰 사용량·이벤트 순서·비밀값 없는 /goal 원문은 보존한다. 실패나 추가 지시를 숨기거나 성과·검증 결과를 만들지 않는다. 자동 사이트 로그인, 내부망 접근, 임의 URL 크롤링, 실제 업무 시스템 수정, 별도 유료 플랜 가입, 구매, 실제 데이터 영구 저장은 이번 범위에서 제외한다. 업로드 이미지의 외부 AI 전송을 사용자에게 알리고 불필요하게 영구 보관하지 않는다. 공개 API에는 입력 크기·호출 시간·사용량에 대한 합리적인 제한을 두고 실제 보장 범위를 기록한다.

5. 판단 범위
기존 ux-check 안의 설계, 화면 구성, 코드 작성·수정, 라이브러리 선택, 합성 예제 제작, 테스트, 기존 Claude API의 필요한 실제 호출, 커밋과 공개 GitHub push, 연결된 Vercel 프로젝트 배포, 문서·영상·발표자료 준비와 검증은 에이전트가 스스로 진행한다. 다른 기존 프로젝트는 변경하지 않는다. 구현 난관이 있으면 같은 사용자 결과를 만족하는 단순하고 안정적인 방법을 선택하고 이유를 기록한다. 새 계정 로그인, 사용자만 할 수 있는 인증, 새로운 결제·유료 계약, 권한의 중대한 확대, 실제 업무 정보의 외부 전송, 되돌리기 어려운 삭제는 진행하지 않고 내일 확인할 항목에 구체적인 이유와 필요한 조작을 남긴다. 이 항목 하나 때문에 독립적으로 가능한 개발과 검증을 멈추지 않는다. 대회 최종 제출 버튼은 누르지 않고 사용자가 정오 전에 검토·제출할 수 있도록 준비한다. 목표나 범위를 변경해야 하면 변경 이유와 영향을 기록한다.

6. 검증과 종료
먼저 실제 작동하는 최소 사용자 흐름을 구현·배포하고, 사용자 관점에서 실행해 결과를 확인한다. 실패하면 재현 조건과 원인을 기록하고 수정한 뒤 해당 검증을 다시 실행한다. 한 가지 접근이 반복 실패하면 원인을 분석해 다른 방법으로 진행한다. 필수 흐름이 동작한 뒤에도 남은 시간 동안 근거의 품질, 비교의 정확성, 오류 복구, 접근성, 모바일 사용성, 보고서 전달성, 성능, 공개 시연과 제출 증거를 실제로 개선한다. 소개에서 안내받은 긴 실행 시간과 많은 토큰 사용을 고려해 충분히 깊게 구현·실험·검증하되, 시간을 채우기 위한 대기·무의미한 반복·토큰 낭비·사용량 조작은 하지 않는다. 2026년 9월 22일 오전 9시(KST)부터는 새로운 대형 기능보다 오류 수정, 회귀 검증, 배포 안정화와 제출 자료에 집중한다. 오전 10시(KST)에 필수 흐름 및 제출 자료의 확인 결과, 남은 제약, 사용자의 최종 조작 목록을 정리해 인계한다. 필수 기준을 충족하지 못했거나 사용자 조작이 남으면 완료로 가장하지 말고 실제 동작 범위와 미완료 사유를 명확히 보고한다.
